The response latency metric checks whether your voice agent **answers without a long wait**: the caller finishes speaking and doesn't sit in silence before the agent starts its reply. It returns the share of agent replies that started in time, between 0 and 1.

<AudioSample name="response-latency" />

## Required Arguments

To use the `ResponseLatencyMetric`, you'll have to provide a [`ConversationalTestCase`](/docs/evaluation-multiturn-test-cases) with audio on at least one of:

- `audio` on the test case, a stereo recording of the whole call
- `audio` on the caller's and agent's turns, each with a `start_time`

Agent turns can also carry `latency_ms`, the response latency your connector recorded for that reply. It's only used with per-turn audio.

Read the [How Is It Calculated](#how-is-it-calculated) section below to learn how each is used.

## Usage

The `ResponseLatencyMetric()` can be used for [end-to-end](/docs/evaluation-end-to-end-multi-turn) evaluation of voice calls, such as ones produced by the [`ConversationSimulator` in voice mode](/docs/conversation-simulator-voice-mode):

```python
from deepeval import evaluate
from deepeval.dataset import ConversationalGolden
from deepeval.metrics import ResponseLatencyMetric
from deepeval.simulator import ConversationSimulator
from deepeval.voice import ElevenLabsConnector, VoiceConfig


golden = ConversationalGolden(
    scenario="The user asks the agent to look up an order by its number.",
    expected_outcome="The agent reads back the order status.",
)

simulator = ConversationSimulator(
    voice_config=VoiceConfig(
        connector=ElevenLabsConnector(agent_id="your-agent-id"),
    )
)
test_cases = simulator.simulate([golden])

metric = ResponseLatencyMetric(threshold=0.8, max_latency_seconds=4)
evaluate(test_cases=test_cases, metrics=[metric])
```

There are **TWO** optional parameters specific to the `ResponseLatencyMetric`, on top of the [common voice metric parameters](/docs/metrics-voice-introduction#using-voice-metrics):

- [Optional] `max_latency_seconds`: an integer for the longest wait, in seconds, between the caller finishing and the agent starting to speak. Must be greater than 0. Defaulted to `4`.
- [Optional] `use_speech_detection`: a boolean which when set to `True`, only counts someone as talking when [speech is detected](/docs/metrics-voice-introduction#speech-detection), so background noise doesn't shorten or stretch a wait. Defaulted to `True`.

### As a standalone

You can also run the `ResponseLatencyMetric` on a single test case as a standalone, one-off execution:

```python
metric.measure(test_cases[0])

print(metric.score, metric.reason)
print(metric.score_breakdown)
```

See [Events](#events) for what `score_breakdown` contains.

Every event also has the [fields all voice events share](/docs/metrics-voice-introduction#events), such as `mark` and `description`. Replies that couldn't be timed are listed under `skipped` with the reason.

`eligible_turns` is how many agent replies were timed and `turns_with_events` how many were slow. The score is the share that weren't.

## How Is It Calculated?

The `ResponseLatencyMetric` score is calculated according to the following equation:

<Equation formula="\text{Response Latency} = \frac{\text{Number of Agent Replies Within the Wait Limit}}{\text{Total Number of Timed Agent Replies}}" />

The metric reads [full call audio or per-turn audio](/docs/metrics-voice-introduction#full-call-audio-vs-per-turn-audio), and the two find replies and measure waits differently, as below.

An opening line the agent speaks before the caller makes any sound answers no one, so it isn't counted. [Time to First Response](/docs/metrics-time-to-first-response) times it instead.

</Tab>

### Latency criteria

The wait runs from where the caller's speech ends to where the agent's speech starts.

<Tabs items={["Full call audio", "Per-turn audio"]}>
<Tab value="Full call audio">

<VoiceDiagram

  lanes={[

    { label: "Agent", role: "agent", sounds: [{ start: 3.2, end: 4.8 }, { start: 11.8, end: 12 }] },

The wait is the silence between the two channels, from the caller's last sound to the agent's first sound. `latency_ms` on the turns is ignored.

</Tab>

<VoiceDiagram

The metric listens inside each clip for where the speech starts and stops, so silence at the start of the agent's clip still counts as waiting. Above, the clips are only 0.2 seconds apart, but the caller waited 5.1 seconds.

When the agent turn has `latency_ms`, that is the wait instead, and the silence heard isn't used.

</Tab>
</Tabs>

A reply is slow when:

| Check | Rule |
| --- | --- |
| Wait | More than `max_latency_seconds`, 4 seconds by default |
| Overlap | The agent starting up to 0.5 seconds before the caller finishes counts as no wait |

A reply isn't timed, and is listed under `skipped`, when:

- the agent started more than 0.5 seconds before the caller finished, which [Agent Interruption](/docs/metrics-agent-interruption) judges instead,
- with per-turn audio, the caller's or the agent's clip can't be decoded, or
- with per-turn audio, the two clips touch, speech runs right up to where they meet and there's no `latency_ms`, so no silence can be heard.

If there's nothing to count, the metric is [skipped](/docs/metrics-voice-introduction#when-a-metric-is-skipped).

:::note
People answer each other in about 0.2 seconds, and about 1 second of silence is the usual maximum. A voice agent also has to transcribe, think and speak, so the default allows 4 seconds. On real phone calls labelled by human reviewers, 4 seconds matched their judgement best, while 2 seconds flagged almost every call.
:::

      question: "Does this metric call an LLM or an external speech model?",

          small Silero VAD model locally.
        </>
      ),
    },
    {
      question: "Does it check the caller's audio too?",
      answer: (
        <>
          No. The caller's audio is only used to know when the caller stopped
          talking. Only the agent is judged.
        </>
      ),
    },
