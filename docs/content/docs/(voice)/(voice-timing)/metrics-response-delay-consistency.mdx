The response delay consistency metric checks whether your voice agent **takes about the same time to answer every reply**, rather than replying instantly once and making the caller wait seconds the next time. It returns the share of agent replies whose wait stays close to the agent's typical wait, between 0 and 1.

## Required Arguments

To use the `ResponseDelayConsistencyMetric`, you'll have to provide a [`ConversationalTestCase`](/docs/evaluation-multiturn-test-cases) with audio on at least one of:

- `audio` on the test case, a stereo recording of the whole call\*
- `audio` on the caller's and agent's turns, each with a `start_time`

Agent turns can also carry `latency_ms`, used with per-turn audio the same way as in [Response Latency](/docs/metrics-response-latency).

\* Full call audio has to be stereo, with the caller and agent on separate channels. Mono full call audio is ignored, because the two voices can't be told apart.

Read the [How Is It Calculated](#how-is-it-calculated) section below to learn how each is used.

## Usage

The `ResponseDelayConsistencyMetric()` can be used for [end-to-end](/docs/evaluation-end-to-end-multi-turn) evaluation of voice calls, such as ones produced by the [`ConversationSimulator` in voice mode](/docs/conversation-simulator-voice-mode):

```python
from deepeval import evaluate
from deepeval.dataset import ConversationalGolden
from deepeval.metrics import ResponseDelayConsistencyMetric
from deepeval.simulator import ConversationSimulator
from deepeval.voice import ElevenLabsConnector, VoiceConfig


golden = ConversationalGolden(
    scenario="The user asks the agent to look up an order by its number.",
    expected_outcome="The agent reads back the order status.",
)

simulator = ConversationSimulator(
    voice_config=VoiceConfig(
        connector=ElevenLabsConnector(agent_id="your-agent-id"),
    )
)
test_cases = simulator.simulate([golden])

metric = ResponseDelayConsistencyMetric(threshold=0.8, max_shift_seconds=2)
evaluate(test_cases=test_cases, metrics=[metric])
```

There are **TWO** optional parameters specific to the `ResponseDelayConsistencyMetric`, on top of the [common voice metric parameters](/docs/metrics-voice-introduction#using-voice-metrics):

- [Optional] `max_shift_seconds`: an integer for how far, in seconds, a reply's wait may be from the agent's typical wait, slower or faster. Must be greater than 0. Defaulted to `2`.
- [Optional] `use_speech_detection`: a boolean which when set to `True`, only counts someone as talking when [speech is detected](/docs/metrics-voice-introduction#speech-detection), so background noise doesn't shorten or stretch a wait. Defaulted to `True`.

### As a standalone

You can also run the `ResponseDelayConsistencyMetric` on a single test case as a standalone, one-off execution:

```python
metric.measure(test_cases[0])

print(metric.score, metric.reason)
print(metric.score_breakdown)
```

See [Events](#events) for what `score_breakdown` contains.

## Events

Each reply whose wait broke from the usual shows up in `score_breakdown`. Here is what the two calls in the [example call](#example-call) return:

```python
{
    "eligible_turns": 4,
    "turns_with_events": 1,
    "events": [
        {
            "type": "delay_shift",
            "duration_seconds": 4.0,
            "start_time": 12.6,
            "mark": "range",
            "timing_source": "call_recording",
            "description": "Reply came 2.9s slower than usual",
            "reply_start": 16.6,
            "response_delay_seconds": 4.0,
            "shift_seconds": 2.9,
        }
    ],
    "skipped": [],
    "timing_source": "call_recording",
}
```

| Field | What it means |
| --- | --- |
| `reply_start` | When the reply started, in seconds into the call |
| `response_delay_seconds` | How long the caller waited for it |
| `shift_seconds` | How far that wait is from the typical wait. Negative when faster |
| `start_time` | Where the wait begins: when the caller stopped talking |
| `duration_seconds` | How long the wait lasted, the same as `response_delay_seconds` |

Every event also has the [fields all voice events share](/docs/metrics-voice-introduction#events), such as `mark` and `description`. Replies that couldn't be timed are listed under `skipped` with the reason.

`eligible_turns` is how many agent replies were timed and `turns_with_events` how many broke from the usual wait. The score is the share that didn't.

## How Is It Calculated?

The `ResponseDelayConsistencyMetric` score is calculated according to the following equation:

<Equation formula="\text{Response Delay Consistency} = \frac{\text{Number of Agent Replies Close to the Typical Wait}}{\text{Total Number of Timed Agent Replies}}" />

With per-turn audio instead of a call recording, the waits are measured the same way, from the speech heard inside each clip, placed on the call's clock by its `Audio.start_time`. Events name the agent turn instead of a time in the call.

### Counting agent replies

Replies are found and their waits measured exactly as in [Response Latency](/docs/metrics-response-latency#counting-agent-replies), and the same replies are left out and listed under `skipped`.

The typical wait is the median of all the replies' waits, so one odd reply is flagged on its own rather than moving the rest. Above, the typical wait is 1.15 seconds, and only reply 3 is far from it.

| Check | Rule |
| --- | --- |
| Shift | More than `max_shift_seconds` from the typical wait, 2 seconds by default, slower or faster |
| Replies needed | At least 3 timed replies. With fewer, there's no telling which one is off |

With fewer than 3 timed replies, or nothing to count, the metric is [skipped](/docs/metrics-voice-introduction#when-a-metric-is-skipped).

:::note
A reply can pass [Response Latency](/docs/metrics-response-latency) and still be flagged here. A 3.8-second wait is under the 4-second latency limit, but stands out after a string of 1-second replies.
:::

          often because the agent answered before the caller had finished
