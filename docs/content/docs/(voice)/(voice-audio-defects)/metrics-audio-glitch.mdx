The audio glitch metric checks whether your voice agent's audio **carried sounds nobody meant to make**. It runs four single-issue voice metrics for held tones, dead stream, cut-offs and clipping on the agent's replies, and returns the share of replies none of them flagged, between 0 and 1.

:::note
This metric exists because a transcript cannot show these failures. A text-to-speech engine that emits a buzzing tone after a sentence, or a stream that drops to digital silence mid-answer, leaves nothing for a speech-to-text model to write down — the model either skips the sound or guesses the words it expected. Detection here is signal analysis over the audio samples.
:::

## Usage

Voice metrics evaluate calls produced by the [`ConversationSimulator` in voice mode](/docs/conversation-simulator-voice-mode), or any `ConversationalTestCase` whose turns carry [`Audio`](/docs/evaluation-voice#audio-data-model) clips. Start with one `ConversationalGolden`, simulate one call, then hand what it returns to `evaluate()`:

```python
from deepeval import evaluate
from deepeval.dataset import ConversationalGolden
from deepeval.metrics import AudioGlitchMetric
from deepeval.simulator import ConversationSimulator
from deepeval.voice import ElevenLabsConnector, VoiceConfig


golden = ConversationalGolden(
    scenario="The user asks the agent to confirm their start date.",
    expected_outcome="The agent reads back the date and asks a follow-up.",
)

simulator = ConversationSimulator(
    voice_config=VoiceConfig(
        connector=ElevenLabsConnector(agent_id="your-agent-id"),
    )
)
test_cases = simulator.simulate([golden])

metric = AudioGlitchMetric(threshold=0.8)
evaluate(test_cases=test_cases, metrics=[metric])
```

There are **SIX** optional parameters when creating an `AudioGlitchMetric`:

- [Optional] `threshold`: a number representing the minimum passing score. Set it to `None` to run the metric in [score-only mode](/docs/metrics-introduction#metric-thresholds). Defaulted to `0.5`.
- [Optional] `include_reason`: a boolean which, when set to `True`, includes a summary of the evaluation score. Defaulted to `True`.
- [Optional] `strict_mode`: a boolean which, when set to `True`, requires a perfect score. Any score below 1 becomes 0, and the threshold is set to 1. Defaulted to `False`.
- [Optional] `verbose_mode`: a boolean which, when set to `True`, includes the score breakdown in verbose metric logs. Defaulted to `False`.
- [Optional] `use_speech_detection`: a boolean which, when set to `True`, only counts the caller as talking when the sound on their channel is speech, so background noise is not mistaken for the caller. Only applies with a stereo `call_recording_path`, and is passed to the [Abrupt Cut-off](/docs/metrics-abrupt-cut-off) check. Defaulted to `True`.
- [Optional] `flaky`: a boolean which, when set to `True`, [marks the metric as flaky](/docs/metrics-introduction#flaky-metrics). Defaulted to `False`.

`model`, `async_mode` and `evaluation_template` are still accepted, so code written when an LLM wrote this metric's reason keeps working, but they are ignored.

Every voice metric records what it measured on `score_breakdown`. Read it after a standalone `measure()` call, or turn on `verbose_mode` to have it printed during an `evaluate()` run:

```python
metric.measure(test_cases[0])

print(metric.score)  # e.g. 0.75
print(metric.score_breakdown)
```

For `AudioGlitchMetric` the breakdown counts the replies, lists every issue found, and gives each part's own result:

```python
{
    "eligible_turns": 4,
    "turns_with_events": 1,
    "events": [
        {"type": "held_tone", "turn": 3, "role": "assistant", "offset_seconds": 2.0, "duration_seconds": 1.5, "start_time": 12.5, "position": "middle", "pitch_hz": 388.0, "periodicity": 0.998, "level_dbfs": -17.2, "jitter": 0.0004, "glide": 0.001, "hold_ratio": 4.1, "pitch_ratio": 1.69, "metric": "Held Tone"},
    ],
    "skipped": [],
    "metrics": {
        "Held Tone": {"score": 0.75, "eligible_turns": 4, "turns_with_events": 1},
        "Dead Stream": {"score": 1.0, "eligible_turns": 4, "turns_with_events": 0},
        "Abrupt Cut-off": {"score": 1.0, "eligible_turns": 4, "turns_with_events": 0},
        "Audio Clipping": {"score": 1.0, "eligible_turns": 4, "turns_with_events": 0},
    },
}
```

`eligible_turns` is how many agent replies were judged and `turns_with_events` how many had at least one issue. `events` holds each part's events unchanged, tagged with the `metric` that raised them; the part's own page explains its fields, and `start_time` places each one on the call's clock so the moment can be found in the recording. `skipped` collects the replies a part could not judge, such as agent audio that could not be decoded. `metrics` gives each part's own `score`, `eligible_turns` and `turns_with_events`, or `{"score": None, "reason": ...}` when that part could not judge the call. The reason for the call above reads "1 of 4 agent replies had an issue: Held Tone (1)."

## How Is It Calculated?

`AudioGlitchMetric` runs these single-issue metrics on the call, each with its default limits:

| Part                                           | Flags an agent reply that                                     |
| ---------------------------------------------- | ------------------------------------------------------------- |
| [Held Tone](/docs/metrics-held-tone)           | contains a stuck tone or drone.                               |
| [Dead Stream](/docs/metrics-dead-stream)       | goes completely dead partway through.                         |
| [Abrupt Cut-off](/docs/metrics-abrupt-cut-off) | stops mid-sound, including a stream cut the agent picked up again. |
| [Audio Clipping](/docs/metrics-audio-clipping) | is distorted from being too loud.                             |

The score is the share of judged agent replies that none of the parts flagged:

<Equation formula="\text{Audio Glitch} = 1 - \frac{\text{Agent replies flagged by at least one part}}{\text{Agent replies judged}}" />

A reply flagged by two parts counts once. Only the agent's replies are judged; the caller's audio is not scored. A reply whose audio cannot be decoded is listed under `skipped` rather than failed, and a call with no audio at all is skipped. The reason is fixed text built from the counts, so the same call always gets the same reason.

With a stereo call recording (`call_recording_path`), cut-offs are read from the recording, and each one counts against the agent reply that started last before the cut. A cut before the test case's first agent reply, such as one in turns left out of the test case, is not counted. That needs `start_time` on every audio turn; without it, cut-offs are read from each reply's own audio.

:::caution
Production clips are usually cut at the speech-to-text engine's turn boundaries. An artifact the agent's TTS emits _after_ the last word — the common case — lands after the agent's end timestamp, so make sure each clip runs until the next speaker starts, or it will never be inside a clip for this metric to find.
:::
