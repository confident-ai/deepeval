The fallback correctness metric uses LLM-as-a-judge to evaluate whether an agent responds safely and usefully when it cannot complete a task normally. Typical cases include a tool timeout, an empty retrieval result, missing required information, or insufficient evidence. It is a self-explaining LLM-Eval, meaning it outputs a reason for its score.

:::info
The `FallbackCorrectnessMetric` is a **community metric**, contributed and maintained by the `deepeval` community. Community metrics are not exported from `deepeval.metrics` — import them explicitly from `deepeval.metrics.community` instead.
:::

## Required Arguments

To use the `FallbackCorrectnessMetric`, provide the following arguments when creating an [`LLMTestCase`](/docs/evaluation-test-cases#llm-test-case):

- `input`
- `actual_output`
- `context`

Use `context` to describe the known failure, limitation, available evidence, and any behavior the agent must avoid. You can optionally provide `tools_called`; their inputs and outputs are included as additional evidence for the judge.

## Usage

```python
from deepeval import evaluate
from deepeval.metrics.community import FallbackCorrectnessMetric
from deepeval.test_case import LLMTestCase, ToolCall

metric = FallbackCorrectnessMetric()
test_case = LLMTestCase(
    input="Where is order 123, and when will it arrive?",
    actual_output=(
        "I couldn't retrieve order 123 because the lookup timed out. "
        "I don't have a verified delivery date; please try again shortly."
    ),
    context=[
        "The order-status tool timed out and returned no order data.",
        "The agent must not claim an order status or delivery date without tool evidence.",
    ],
    tools_called=[
        ToolCall(
            name="get_order_status",
            input_parameters={"order_id": "123"},
            output={"error": "timeout"},
        )
    ],
)

# To run the metric as a standalone evaluation:
# metric.measure(test_case)
# print(metric.score, metric.score_breakdown, metric.reason)

evaluate(test_cases=[test_case], metrics=[metric])
```

There are seven optional parameters when creating a `FallbackCorrectnessMetric`:

- [Optional] `threshold`: the minimum passing score. Set it to `None` for [score-only mode](/docs/metrics-introduction#metric-thresholds). The default is `1.0`, which requires all three fallback criteria to pass.
- [Optional] `model`: a string specifying which model to use, or [a custom LLM](/docs/metrics-introduction#using-a-custom-llm) of type `DeepEvalBaseLLM`. Defaults to <DefaultLLMModel />.
- [Optional] `include_reason`: whether to include the judge's reason for the score. Defaulted to `True`.
- [Optional] `async_mode`: whether to enable [concurrent execution within `measure()`](/docs/metrics-introduction#measuring-metrics-in-async). Defaulted to `True`.
- [Optional] `strict_mode`: when `True`, returns `1` only for a perfect score and `0` otherwise, and sets the threshold to `1`. Defaulted to `False`.
- [Optional] `verbose_mode`: whether to print the verdict, score breakdown, and reason. Defaulted to `False`.
- [Optional] `flaky`: whether to [mark the metric as flaky](/docs/metrics-introduction#flaky-metrics). Defaulted to `False`.

## How Is It Calculated?

The judge evaluates three independent criteria:

1. **Acknowledges limitation**: the response accurately communicates the relevant failure, limitation, or uncertainty.
2. **Avoids unsupported claims**: the response does not invent facts or tool results, hide a material failure, or falsely claim task completion.
3. **Appropriate recovery action**: the response takes a useful and safe next step, such as asking for required information, suggesting a retry, offering a supported alternative, providing a qualified partial result, or stopping when proceeding would be unsafe.

Each criterion contributes one third of the final score. `score_breakdown` exposes the individual criterion scores for debugging and failure analysis.
